I measured my agent’s code reviewer before I trusted it

In an agent that merges its own work, the reviewer decides what lands. I wanted to know how good mine was, and whether a different method would be better, before changing anything.

12 November 2026 · Taejin Jung

The question

My agent’s changes are reviewed by a different model from the one that wrote them. If the review raises an issue, the change goes back to be fixed, for up to three rounds. That had been running for weeks and looked healthy: in fourteen days, 388 runs were reviewed and 71% passed on the first review.

A pass rate does not say whether the reviewer finds what is there. So I asked a narrower question: on the same code, does another method find more real defects than the one I have?

The rule came first

Before running anything, I wrote down what would count as better:

  • The new method must find at least 10 percentage points more real defects than the current loop.
  • It may add at most one false finding per run, because every false finding costs a fix round.
  • Any new finding that decides the result is read by hand.

Writing the rule first matters. With the numbers already in front of me, almost any result could have been argued into a win.

The setup

  • Twelve real runs, one per task: six where a later round had raised an issue, and six that merged after one review.
  • The same code for everyone. Each reviewer saw the first candidate of each run, read-only.
  • Four reviewers with the same prompt: Claude twice, and two Codex models. 48 runs, none failed.
  • A blind judge. One session per sample received every finding shuffled, with no source named, read the code at that commit, and marked each finding real or not. I then read its list by hand and removed two of 28, leaving 26 defects.

The result

MethodReal defects foundAgainst the loop
The loop as it was, up to three rounds11 of 26
First round + Claude again, run a13 of 26+8 points
First round + Claude again, run b18 of 26+27 points
First round + a second reviewer (Codex)15 of 26+16 points
First round + both18 of 26+27 points

Twelve samples, 26 known defects. Most of the defects are small: a missing test a task asked for, a small visual miss.

A second independent look on the first round passed the rule. I adopted the Codex reviewer for it: it tied on defects found, had the fewest false findings of any reviewer (0.08 per run), and runs on a different subscription from the one that limits the loop. It has since reviewed 239 first-round candidates in the live loop.

The row that changed how I measure

Look at the second and third rows. They are the same model with the same prompt on the same code, and they differ by 19 points. The gap between two runs of one reviewer was as large as the gap between any two reviewers.

So the result does not show that another vendor’s model finds more. It shows that a second independent look finds more, whoever takes it. It also means a single run of an evaluation like this cannot tell a real improvement from luck.

Turning the experiment into a tool

The experiment was one script in a temp folder. I rebuilt it as a command, review-eval, with the lessons built in.

  • A fixed answer key. The twelve cases and 26 defects live in one file that only a human pull request may change, so the agent cannot edit its own answer key.
  • The loop’s real code. The tool calls the same review functions the loop calls. A change to the review prompt shows up in the score without touching the tool.
  • A judge that matches, and does not define. It maps findings to known defects. Anything new is printed for a person to read and never moves the score on its own.
  • Noise is reported. Every evaluation runs at least twice and prints the spread. A change is adopted only if its gain is larger than the spread of both runs.
  • A tool, never a gate. No part of the agent reads the answer key or the results. A person runs it.

Limits

Twelve samples is small, seven of them come from one page of the product, and the judge is itself a model. I treat the percentages as rough, which is why the next step is growing the set to about thirty cases from other areas before it decides much more.

What I took from it

An agent’s reviewer is a component like any other, and it deserves a test of its own. The useful habits were ordinary ones: decide the rule before the run, keep the answer key out of the system’s reach, and report the noise next to the number.
