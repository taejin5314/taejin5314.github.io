Taejin Jung Work Writing Résumé

A third of my agent’s time was rework. I did not add more agents.

The obvious way to make an autonomous coding agent faster is to run more of them. I measured a session first, and the measurement pointed somewhere else.

12 November 2026 · Taejin Jung

The rule that makes it safe

My agent picks an approved task, writes the change, runs the checks, has a different model review it, and merges. Nobody watches it. What makes that acceptable is one strict rule at the end: it may push only the exact merge commit it verified, and only if main is still the exact commit it verified against. The push carries a lease on that commit, so if anything else has landed, the push fails.

I would not give that rule up. It is the reason I can let the agent merge at all.

Where the time went

On 9 and 10 October I measured fifteen runs in a row from the agent’s own logs: ten merges in 258 minutes. Then I sorted the minutes by what they were spent on.

From the agent’s monitor, event and report logs. The categories overlap, so the column does not add up to 100.

The top row was the surprise. In four of the fifteen runs, the agent finished, passed every check, passed review, and then found that main had moved, because I had merged a pull request of my own in the meantime. The rule did its job and refused the push. The run then started again from nothing: a fresh baseline, a fresh choice of task, a fresh implementation. In all four, the files the agent had touched and the files I had touched did not overlap.

Three options

Run more agents in parallel. This is what I had planned to do. The numbers argued against it. Every agent draws on the same usage limit, and one loop already used about 14% of a five-hour window each hour. Two loops would hit the limit in about three hours, for an estimated 1.2 times the output. And with a lease on the exact base commit, two changes built on the same base cannot both merge anyway.

Leave it as it was. Safe, but it kept redoing the work most likely to be right: work that had already passed every gate.

Carry the finished change forward. Merge queues keep an author’s work when the target moves and test the combination again. Gerrit carries a review across a rebase only when the rebase is trivial. Both are the same idea: the work is still good, so prove it against the new base instead of throwing it away.

What I built

The third option, with the rule untouched.

  • When main has moved, the harness rebuilds the change on the new base with a three-way merge. A conflict ends the run, as before.
  • Every check runs again on the rebuilt change, in a fresh export. A failure ends the run.
  • The review carries over only if the patch itself is unchanged, compared by a stable patch ID. If it differs, the reviewer reads it again.
  • The push still carries the same lease. Nothing about what is allowed to land has changed.

The speed comes from keeping good work, with the same gates.

Every one of the 96 had an identical patch, which matches what the first four showed: when my work and the agent’s work collide in time, they almost never collide in content.

What I took from it

Measure where the time goes before choosing how to go faster. I had a plan, the plan was more agents, and fifteen runs of data showed that the plan would have bought very little while the real cost sat in a place I had not looked. The fix was also the smaller change: no new agents, no looser rule, one new path through code that already existed.
